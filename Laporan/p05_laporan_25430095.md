## 2. Ringkasan Dasar Teori
Data Definition Language (DDL) merupakan sub-bahasa SQL yang bertanggung jawab langsung dalam mendefinisikan, mengubah, dan menghapus kerangka fisik penyimpanan data di dalam DBMS. Pemilihan tipe data dalam DDL merupakan keputusan perancangan fundamental; penentuan tipe data yang berlebihan memboroskan ruang penyimpanan dan memori buffer server, sementara tipe data yang terlalu sempit akan menolak data valid di kemudian hari.

Penerapan *constraint* bertujuan memindahkan penegakan integritas data dari ketergantungan pada kedisiplinan pemrogram aplikasi (*client-side validation*) menuju jaminan absolut pada tingkat mesin basis data (*server-side enforcement*). Sejak MariaDB versi 10.2+, klausa `CHECK` telah dievaluasi dan ditegakkan secara aktif oleh server, sehingga batasan nilai kolom non-negatif atau rentang tertentu dapat dicegah langsung sebelum data disimpan ke disk. 

Dalam arsitektur basis data relasional yang saling terikat oleh kunci tamu (*Foreign Key*), terdapat aturan ketergantungan yang kaku:
1. **Urutan Pembuatan Tabel:** Tabel induk (*parent table*) wajib didefinisikan terlebih dahulu sebelum tabel anak (*child table*) yang merujuknya dibuat.
2. **Urutan Penghapusan Tabel:** Tabel anak wajib dihapus terlebih dahulu sebelum tabel induk dapat dijatuhkan, guna mencegah terjadinya pelanggaran integritas referensial (*orphaned references*).

## 3. Hasil Langkah Percobaan (Kasus Kopma)

### 3.1 Pembuatan Skrip DDL Kopma (`kopma_095`)
Skrip DDL studi kasus Koperasi Mahasiswa Sejahtera diimplementasikan pada berkas `p05_ddl_kopma_25430095.sql`. Struktur tabel diawali dengan blok penghapusan terbalik dan disusul dengan pembuatan 8 tabel terhubung:

```sql
USE kopma_095;

-- Urutan DROP TABLE terbalik (Anak ke Induk)
DROP TABLE IF EXISTS detail_pembelian;
DROP TABLE IF EXISTS pembelian;
DROP TABLE IF EXISTS detail_penjualan;
DROP TABLE IF EXISTS penjualan;
DROP TABLE IF EXISTS pemasok;
DROP TABLE IF EXISTS barang;
DROP TABLE IF EXISTS anggota;
DROP TABLE IF EXISTS petugas;

-- Pembuatan Tabel Induk
CREATE TABLE petugas (
    id_petugas SMALLINT NOT NULL AUTO_INCREMENT,
    kode_petugas CHAR(3) NOT NULL,
    nama_petugas VARCHAR(100) NOT NULL,
    peran_petugas ENUM('kasir', 'gudang', 'ketua') NOT NULL,
    PRIMARY KEY (id_petugas),
    UNIQUE KEY uq_petugas_kode (kode_petugas)
) ENGINE=InnoDB;

CREATE TABLE barang (
    id_barang INT NOT NULL AUTO_INCREMENT,
    kode_barang VARCHAR(10) NOT NULL,
    nama_barang VARCHAR(100) NOT NULL,
    kategori_barang ENUM('ATK', 'makanan', 'minuman') NOT NULL,
    harga_jual_barang DECIMAL(12,2) NOT NULL,
    stok_barang INT NOT NULL DEFAULT 0,
    stok_min_barang INT NOT NULL DEFAULT 5,
    PRIMARY KEY (id_barang),
    UNIQUE KEY uq_barang_kode (kode_barang),
    CONSTRAINT ck_barang_stok CHECK (stok_barang >= 0),
    CONSTRAINT ck_barang_harga CHECK (harga_jual_barang >= 0),
    CONSTRAINT ck_barang_stok_min CHECK (stok_min_barang >= 0)
) ENGINE=InnoDB;
```

### 3.2 Pembuktian Penegakan Constraint Server
Untuk menguji bahwa constraint pada MariaDB bekerja dengan efektif, dijalankan tiga skenario uji pelanggaran aturan data:

#### Uji 1: Pelanggaran Kunci Tamu (Foreign Key)
Mencoba mencatat penjualan dengan `id_petugas = 99` yang tidak terdaftar pada tabel induk `petugas`:
```sql
INSERT INTO penjualan (no_nota_penjualan, tgl_penjualan, id_petugas, id_anggota, bayar_penjualan)
VALUES ('PJ-2609-0199', NOW(), 99, NULL, 5000);
```
**Hasil Terminal:**
```text
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails 
(`kopma_095`.`penjualan`, CONSTRAINT `fk_penjualan_petugas` FOREIGN KEY (`id_petugas`) REFERENCES `petugas` (`id_petugas`))
```
*Keterangan:* Server berhasil menolak transaksi karena integritas referensial mendeteksi ketiadaan baris induk yang valid.

#### Uji 2: Pelanggaran Batas Nilai Negatif (CHECK Constraint)
Mencoba mengubah stok barang menjadi minus satu (`-1`), melanggar aturan bisnis AB-03:
```sql
UPDATE barang SET stok_barang = -1 WHERE id_barang = 1;
```
**Hasil Terminal:**
```text
ERROR 4025 (23000): CONSTRAINT `ck_barang_stok` failed for `kopma_095`.`barang`
```
*Keterangan:* MariaDB 10.4 menegakkan evaluasi `CHECK (stok_barang >= 0)` dan membatalkan pembaruan data secara otomatis.

#### Uji 3: Pelanggaran Keunikan Kode (UNIQUE Constraint)
Mencoba memasukkan barang baru dengan kode `ATK-001` yang telah terdaftar di database:
```sql
INSERT INTO barang (kode_barang, nama_barang, kategori_barang, harga_jual_barang)
VALUES ('ATK-001', 'Pulpen Duplikat', 'ATK', 3500);
```
**Hasil Terminal:**
```text
ERROR 1062 (23000): Duplicate entry 'ATK-001' for key 'uq_barang_kode'
```
*Keterangan:* Indeks unik menolak perekaman baris duplikat sehingga konsistensi kode barang terjamin.

### 3.3 Modifikasi Struktur Kolom (`ALTER TABLE`)
Pengujian modifikasi skema tabel barang untuk pencatatan tanggal kedaluwarsa:
```sql
-- Menambahkan kolom tgl_kedaluwarsa setelah kolom stok_min_barang
ALTER TABLE barang ADD COLUMN tgl_kedaluwarsa DATE NULL AFTER stok_min_barang;

-- Membatalkan dan menghapus kolom tersebut kembali
ALTER TABLE barang DROP COLUMN tgl_kedaluwarsa;
```

## 4. Jawaban Titik Analisis

### Titik Analisis 1: Perbedaan Klausa `ON DELETE` pada Tabel Relasi
* **Pertanyaan:** Mengapa `fk_detail_penjualan` memakai `ON DELETE CASCADE`, sedangkan `fk_detail_barang` tidak? Apa yang terjadi pada laporan penjualan lama jika barang boleh dihapus beserta seluruh detailnya?
* **Jawaban:**  
  1. `fk_detail_penjualan` menghubungkan `detail_penjualan` ke `penjualan`. Hubungan ini bersifat *komposisi kuat*: baris detail penjualan tidak memiliki makna eksistensi mandiri tanpa adanya nota penjualan induk. Apabila sebuah transaksi penjualan dibatalkan atau dihapus dari sistem, maka wajar seluruh rincian item di dalam nota tersebut ikut dihapus secara otomatis (`ON DELETE CASCADE`).
  2. Sebaliknya, `fk_detail_barang` menghubungkan detail transaksi ke master `barang`. Hubungan ini bersifat *referensial*. Jika pada relasi ini dipasang `ON DELETE CASCADE`, maka ketika seorang petugas gudang menghapus suatu item barang dari katalog, **seluruh rekaman transaksi historis masa lalu di tabel detail_penjualan yang pernah memuat barang tersebut akan ikut terhapus permanen dari basis data!**
  3. Konsekuensinya terhadap laporan: Rekapitulasi omzet penjualan tahun lalu akan rusak dan menyusut secara tidak wajar, bukti audit keuangan hilang, dan integritas laporan historis koperasi tidak dapat dipertanggungjawabkan lagi. Oleh karena itu, foreign key ke barang wajib memakai aksi bawaan `RESTRICT` / `NO ACTION` agar server menolak penghapusan barang yang memiliki jejak transaksi historis (Error 1451).

### Titik Analisis 2: Pemetaan Kode Galat dan Analisis Utang Desain
* **Pertanyaan:** Petakan kode galat 1452, 4025, dan 1062 ke aturan bisnis (AB-xx) yang dilindunginya. Aturan bisnis Kopma mana yang belum dapat dijaga oleh constraint apa pun?
* **Jawaban:**  
  1. **ERROR 1452 (`Cannot add or update a child row`)**: Melindungi aturan bahwa setiap nota penjualan wajib dilayani oleh kasir/petugas yang sah dan terdaftar pada entitas `petugas`.
  2. **ERROR 4025 (`CONSTRAINT failed`)**: Melindungi aturan bisnis **AB-03** ("Stok barang tidak boleh bernilai negatif").
  3. **ERROR 1062 (`Duplicate entry`)**: Melindungi integritas keunikan kode barang dan identitas nota (menjamin AB-01 dan AB-05).
  * **Aturan Bisnis Kopma yang BELUM Dapat Dijaga Constraint Tabel:**
    * **AB-03 (Bagian Kedua):** *"Penjualan ditolak bila qty melebihi stok tersedia."* Constraint `CHECK` pada MariaDB hanya mengevaluasi kolom di baris yang sama. MariaDB tidak mengizinkan kueri subquery di dalam `CHECK` untuk membandingkan `qty_detail_penjualan` dengan `stok_barang` di tabel lain saat transaksi kasir berlangsung.
    * **AB-01 (Bagian Kedua):** *"Setiap nota memiliki minimal satu baris barang."* Pada saat baris kepala nota diinsert ke tabel `penjualan`, baris detail belum dimasukkan. Constraint skema tabel tidak dapat memastikan bahwa setelah nota terbuat, kasir pasti menginput minimal satu baris detail.
    * **AB-06:** *"Pesanan pembelian dibuat bila stok kurang dari batas minimum."* Merupakan logika otomasi alur kerja (*triggering workflow*) yang melampaui kemampuan DDL statis.
    *(Catatan: Aturan-aturan ini dicatat sebagai **utang desain** yang akan ditangani menggunakan unit transaksi terkelola `START TRANSACTION` dan `ROLLBACK` pada Modul 14).*

### Titik Analisis 3: Urutan Eksekusi `DROP TABLE IF EXISTS`
* **Pertanyaan:** Mengapa `DROP TABLE IF EXISTS` harus dimulai dari `detail_pembelian` dan `detail_penjualan`, bukan dari `petugas`? Apa pesan galat yang muncul jika urutannya dibalik?
* **Jawaban:**  
  Tabel `petugas`, `anggota`, `barang`, dan `pemasok` bertindak sebagai tabel induk yang dijadikan rujukan oleh kunci tamu pada tabel transaksi dan detail transaksi. DBMS secara ketat melarang penghapusan tabel induk yang masih memiliki tabel anak yang aktif merujuk kepadanya.
  Jika urutannya dibalik (mencoba menghapus `petugas` terlebih dahulu), MariaDB akan menolak eksekusi dan memunculkan galat:
  `ERROR 3730 (HY000): Cannot drop table 'petugas' referenced by a foreign key constraint 'fk_penjualan_petugas' on table 'penjualan'.`  
  Oleh sebab itu, skrip yang dapat dijalankan ulang secara bersih (*idempotent*) wajib mendahulukan penghapusan tabel anak terdalam (tabel detail), lalu tabel transaksi, dan diakhiri oleh tabel master induk.

## 5. Hasil Latihan dan Modifikasi

### 5.1 Latihan 1: Constraint CHECK pada Stok Minimum Barang
Menambahkan batasan bahwa batas minimum stok barang tidak boleh bernilai negatif:
```sql
ALTER TABLE barang ADD CONSTRAINT ck_barang_stok_min CHECK (stok_min_barang >= 0);
```
**Perintah Pembuktian Penolakan:**
```sql

```
**Pesan Galat yang Dihasilkan:**
```text
ERROR 4025 (23000): CONSTRAINT `ck_barang_stok_min` failed for `kopma_095`.`barang`
```
*Analisis:* Constraint `ck_barang_stok_min` terbukti aktif mencegah kesalahan input nilai ambang batas pemesanan ulang.

### 5.2 Latihan 2: Implementasi `ON DELETE SET NULL` pada Relasi Anggota
Memodifikasi kunci tamu `fk_penjualan_anggota` pada tabel `penjualan`:
```sql
ALTER TABLE penjualan DROP FOREIGN KEY fk_penjualan_anggota;
ALTER TABLE penjualan ADD CONSTRAINT fk_penjualan_anggota 
    FOREIGN KEY (id_anggota) REFERENCES anggota (id_anggota) 
    ON DELETE SET NULL;
```
**Analisis Kesesuaian dengan AB-02 dan UU Perlindungan Data Pribadi (UU PDP):**
1. **Kesesuaian dengan AB-02:** Aturan bisnis AB-02 memperbolehkan transaksi penjualan kepada pembeli umum tanpa anggota (`id_anggota` bernilai `NULL`). Ketika relasi diatur menjadi `ON DELETE SET NULL`, penghapusan suatu profil anggota secara otomatis mengubah status transaksi masa lalu yang dilakukannya menjadi transaksi pelanggan umum, tanpa merusak konsistensi relasional.
2. **Kesesuaian dengan UU PDP (UU No. 27 Tahun 2022):** Berdasarkan prinsip perlindungan hak subjek data pribadi (*right to erasure / right to be forgotten*), anggota yang telah lulus atau mengundurkan diri berhak mengajukan permohonan pemusnahan data pribadinya (nama, NIM, no handphone). Dengan aksi `ON DELETE SET NULL`, data pribadi anggota dapat dihapus bersih dari tabel `anggota`, sementara arsip transaksi keuangan koperasi tetap utuh dan akuntabel tanpa melanggar privasi subjek data.

## 7. Pembahasan dan Kendala
Selama implementasi skrip DDL dan constraint pada MariaDB 10.4, beberapa kendala teknis yang dihadapi dan cara penanganannya:
1. **Galat Kunci Tamu (ERROR 1005 errno 150):**  
   * *Penyebab:* Terjadi ketidakcocokan tipe data atau atribut antara kolom kunci tamu dengan kolom kunci primer rujukan (misalnya `id_petugas` di tabel anak didefinisikan bertipe `INT`, sementara di tabel induk bertipe `SMALLINT`).  
   * *Solusi:* Memastikan presisi tipe data, lebar bit, dan penanda tanda bilangan (*signed/unsigned*) sama persis di kedua tabel sebelum mengeksekusi DDL.
2. **Galat Tabel Sudah Ada (ERROR 1050):**  
   * *Penyebab:* Skrip DDL dijalankan berulang kali tanpa adanya instruksi pembersihan tabel lama.  
   * *Solusi:* Menyisipkan blok `DROP TABLE IF EXISTS` di baris awal skrip dengan susunan dari tabel detail/anak ke tabel induk.
3. **Penyusunan Constraint CHECK pada Tanggal:**  
   * Upaya validasi format tertentu pada kolom tanggal dihindari dengan langsung mengadopsi tipe data bawaan `DATE` dan `DATETIME`, yang secara otomatis divalidasi oleh MariaDB ketika mode ketat (`STRICT_TRANS_TABLES`) aktif.

## 8. Kesimpulan
1. DDL dan ragam constraint pada MariaDB 10.4 berhasil mentransformasikan rancangan relasional konseptual menjadi skema fisik yang kokoh, di mana integritas referensial dan validasi nilai terlindungi langsung di tingkat mesin server.
2. Mekanisme `ON DELETE CASCADE` dan `ON DELETE SET NULL` memberikan fleksibilitas pengelolaan siklus hidup data: `CASCADE` ideal untuk entitas asosiatif kepemilikan mutlak (detail transaksi), sedangkan `SET NULL` menjadi solusi tepat untuk menjaga jejak audit operasional sekaligus mematuhi regulasi privasi UU Perlindungan Data Pribadi (UU PDP).
3. Batasan aturan bisnis yang melibatkan agregasi banyak baris (seperti batas pengambilan $P + 2$ mata kuliah pada KRS) tidak dapat ditangani oleh klausa `CHECK` DDL statis, sehingga didelegasikan secara terencana sebagai utang desain pada modul transaksi berikutnya.
